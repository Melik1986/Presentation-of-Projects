## 3. CI/CD как система ограничений

Роль бортинженера, который сигнализирует о проблеме, берёт на себя **человек или автоматизированные проверки в CI**. CI/CD-пайплайн — это система ограничений для кода.

```

Уровень 5: Мониторинг в production
Уровень 4: DAST (динамический анализ)
Уровень 3: SAST + проверки безопасности (Snyk, Gitleaks)
Уровень 2: Качество (тесты, линтер, покрытие)
Уровень 1: Pre-commit hooks (lint-staged, gitleaks)
Уровень 0: Понимание разработчика (вайблёрнинг)

```

### Чеклист перед каждым коммитом

Предполётный чек-лист — обязательная процедура. Пилот с 30 000 часами налёта не пропускает его не потому что не помнит, а потому что человеческая память ненадёжна, а цена ошибки высока.

```

□ Код понятен разработчику (не просто «работает» — понятна причина)
□ Новый код протестирован локально
□ Все тесты проходят (unit + integration)
□ CI YAML валиден и нет allow_failure без обоснования
□ Нет декоративных проверок, ослабляющих безопасность
□ Нет новых зависимостей без обоснования
□ Gitleaks не нашёл секретов
□ git status чист, diff содержит только нужные файлы

````

## 5. Правила качества и безопасности

### 5.1 Никаких устаревших данных обучения

Для API, синтаксиса, паттернов — всегда получать свежую документацию:

1. **Context7 MCP** — структурированная, версионно-осведомлённая документация
2. **Официальная документация** — через web fetch
3. **Реальная кодовая база** — существующие паттерны в репо

### 5.2 Кодовая база — первичный источник

- Изучить кодовую базу **до** предложения паттернов.
- Соответствовать стилю, нейминговым конвенциям, архитектуре.
- Если кодовая база делает X одним способом — не вводить Y без обсуждения.

### 5.3 Анти-галлюцинация

- **НИКОГДА** не выдумывать имена функций, endpoints, параметры.
- **НИКОГДА** не предполагать, что файл существует — верифицировать `read_file`.
- **НИКОГДА** не угадывать синтаксис библиотек — сначала документация.
- При неуверенности: «Мне нужно проверить это» + использовать инструменты.

### 5.4 Обработка ошибок

1. Читать полное сообщение об ошибке — не просматривать по диагонали.
2. Определить корневую причину — не симптомы.
3. Предлагать минимальный фикс — избегать over-engineering.
4. Объяснять фикс — **почему работает**, а не только что делает.

## 8. Git — линейная история (автоматически)

Источник правды: **`.github/gitconfig`** (подключается через `include.path` на `pnpm prepare`).

- Обычный `git pull` / Pull в IDE **сам делает rebase** — без ручного выбора merge/rebase.
- Агент: просто `git pull`, не спрашивать strategy, не предлагать `git config pull.rebase …` ad-hoc.
- Контент-конфликты → стоп; тривиальные → auto-resolve + `rebase --continue`.
- Не `force` на `main`.

**GitHub Ruleset (soft):** `.github/rulesets/main-ai-friendly.json` — нельзя delete/force-push `main`, нужна linear history; без обязательных PR/CI gates. Применить: `corepack pnpm@12.9.1 github:ruleset` (после `gh auth login`). Private free → нужен GitHub Pro или public repo.

### 11.1 TDD — сначала тесты, потом код

- **Red → Green → Refactor**: сначала падающий тест, минимальная реализация, затем рефакторинг без изменения поведения.
- Новая бизнес-логика в `lib/`, `server/`, доменных модулях — **с тестом в том же PR**, если инженер не отменил TDD явно.
- UI/Screen: snapshot/e2e по необходимости; **ядро и use-case** — unit-тесты обязательны.
- Агент не пишет «готовый» модуль без хотя бы одного теста на happy path и один на граничный/ошибочный сценарий.

### 11.2 Разделение UI и бизнес-логики (мобильная разработка)

- **Screen / компонент** — «глупая оболочка»: рендер, навигация, привязка к хукам/стору. Без расчётов, валидации, трансформаций данных внутри `app/**/*.tsx` Screen.
- Расчёты, валидация, маппинг DTO → ViewModel — в `lib/`, `features/*/logic`, хуках use-case, сервисах.
- **Запрет для агента**: `fetch`, сложные `reduce`/`filter` бизнес-смысла, парсинг API, права доступа — внутри Screen-компонента.
- ИИ-задача формулируется так: «логика в `X.ts`, Screen только вызывает `useX()` и отображает».

### 11.3 Functional Core — Imperative Shell (граница–ядро)

Деление кода на две зоны:

| Зона                      | Что внутри                                        | Ограничения                                                                                                                        |
| ------------------------- | ------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| **Функциональное ядро**   | Чистые функции: входные данные → результат        | Без `fetch`, AsyncStorage, Expo-модулей, таймеров, React, побочных эффектов. Синхронно, предсказуемо, тестируется без моков среды. |
| **Императивная оболочка** | Screens, hooks-адаптеры, API-клиенты, БД, таймеры | Получает «грязные» данные с границы → передаёт в ядро → применяет результат (state, навигация, persist).                           |

- Новая фича: сначала чистые функции + тесты, затем тонкая оболочка.
- Путь в репо: ядро — `lib/**`, `features/**/core/**`; оболочка — `app/**`, `hooks/**`, `server/**`.

### 11.4 Error-Driven Design (проектирование от ошибок)

Перед реализацией use-case — **инвентаризация сбоев**:

- сеть оборвалась на полпути;
- HTTP 4xx/5xx, таймаут;
- битый/неполный JSON;
- несовпадение контракта с бэкендом;
- нет прав / сессия истекла;
- background / sleep устройства (мобильный контекст).

**Порядок с ИИ:**

1. TypeScript-типы / discriminated union для всех ошибок модуля.
2. Таблица сценариев: триггер → код ошибки → UX (retry, toast, fallback).
3. Только потом — логика обработки и happy path.

Агент не начинает «оформление заказа» (и аналоги) без явного списка failure modes.

### 11.5 Traceability First (логирование и трейсинг)

- Критичные цепочки (auth, ERP, оплата, sync) — **структурированные логи** с `correlationId` / `step` / длительностью этапа.
- Логи на границе оболочки (до/после вызова ядра), не спам в каждом рендере.
- При баге: инженер даёт лог → агент сопоставляет шаг N с функцией ядра/оболочки.
- Не логировать секреты, PII целиком, токены. Маскирование по политике проекта.

### 11.6 Defensive Programming и контракты (Zod)

- Данные **с сети и из storage** — `safeParse` / `parse` через Zod на **границе** (API client, loader), не глубоко в UI.
- TypeScript на compile-time; Zod на run-time. Расхождение → явная ошибка: «ожидалось `user_id: string`, пришло `number`».
- Не глотать ошибки парсинга; пробрасывать в типизированный `Result` / error union из §11.4.
- Переиспользовать схемы из `lib/schemas`, `server/dto` — не дублировать ad-hoc в Screen.

### 11.7 Feature Flags (флаги возможностей)

- Крупные или рискованные фичи — за флагом (remote config / env / существующий механизм в репо).
- Деплой в prod с флагом **off** → включение для internal/test cohort → rollout для всех без пересборки (где поддерживается OTA/config).
- Агент при добавлении фичи спрашивает: нужен ли flag и кто default audience (off / staff / %).
- Не смешивать flag-check с бизнес-расчётами в ядре: флаг читается в оболочке, ядро получает уже решённый «режим» или не вызывается.

### 11.8 Чеклист агента перед сдачей фичи

```
□ Тесты на ядро (TDD) есть и зелёные
□ Screen без бизнес-логики
□ Чистые функции отделены от fetch/Expo/React
□ Ошибки типизированы до happy path
□ Zod на границе входящих данных
□ Логи с шагами на критичном пути
□ Feature flag — если фича рискованная или поэтапный rollout
```
